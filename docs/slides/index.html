這個專案在驗證什麼

動機

親手實作 Hybrid Search，驗證 Karpathy LLM Wiki 的「編譯知識層 + runtime 檢索」做法。

命題

塔羅——知識範圍有限、結構固定，適合練這套架構；零 DB、檔案型索引。

核心展示

問答 + citation 參考文本：回答必須對應整理過的 wiki，使用者可點擊驗證來源。

可複製性

不限塔羅——客服機器人、內部 SOP、產品說明等有限知識系統都適用同一套做法。

為什麼做

從個人動機出發，不是市場分析

想練的技術，剛好有個好命題

起點很單純：我想親手實作 Hybrid Search，並實際驗證 Karpathy LLM Wiki 這套「把知識編譯成 wiki、runtime 再檢索」的做法，做起來效果到底如何。

我沒有打算長期維護會經常變動的資料庫，所以刻意選了檔案型知識庫。 命題則選了塔羅——當時女友很喜歡塔羅牌，知識範圍有限、結構也相對固定，很適合拿來練習。

從產品構想、架構決策到實作皆一人完成；開發過程主要借助 Codex 協作，方向與程式審閱由我主導。

核心問題

直接丟 LLM 不夠「客觀」

同樣的問題，每次答案可以天差地遠

過去我會直接把問題和牌面一起丟給 LLM 解讀——不只是塔羅，上升星座、紫薇命盤或其他占卜形式也試過。 結果都受限於 LLM 的生成方式，顯得很不穩定。

這對我來說不是一個客觀的系統。我想要的是：回答必須能對應到我整理過的知識， 而且使用者可以回頭查證依據，而不是每次都在賭模型當下的「靈感」。

情境解讀分類與內部連結

三個關鍵決策

當時想解決什麼 → 為什麼沒選 → 最後怎麼選 → 代價

1. LLM Wiki 分層，而不是直接餵 raw 資料

  • 想解決：穩定、可版本控制的知識來源，而不是每次從零生成。
  • 沒選：直接爬牌義丟 LLM，或 runtime 查 raw 檔——格式雜亂、難做有效 chunk 與索引。
  • 最後選：raw/ 不可變原始資料，wiki/ 是 compiled layer；知識更新時重新 compile 與建 index。
  • 代價：需維護 compile pipeline；wiki 品質直接決定回答上限。

2. 零資料庫、檔案型索引

  • 想解決：不想為 side project 長期維護會頻繁變動的 DB。
  • 沒選：PostgreSQL + pgvector、OpenSearch——對 105 篇 wiki、78 張牌，運維成本遠大於收益。
  • 最後選：wiki/**/*.md + BM25 / vector cache / graph.json，全部檔案化、可重建。
  • 代價：corpus 成長後 JSON index 載入變慢；上 production 規模還是得遷移。

3. 寧可 fallback，也要 citation 硬驗證

  • 想解決：同樣輸入得到穩定、可驗證的輸出——對「客觀系統」的最低要求。
  • 沒選：讓 LLM 自由發揮——聽起來合理，但無法確認依據，每次結果還可能不同。
  • 最後選：只能引用檢索到的 chunks，格式 [來源: pageId#chunkId]，回答後硬驗證；失敗回 safety fallback。
  • 代價：回答率較低——驗證失敗時使用者看到 fallback，而不是「總是有話說」。

Hybrid Retrieval

中文口語查詢 vs 結構化 wiki

語意 chunking + hybrid rerank + phrase-aware tokenizer

使用者常以口語中文提問（如「他對我是真心的嗎」），但 wiki 是結構化牌義； 固定字數 chunking 會切碎語意，純 BM25 也難命中「聖杯二逆位」這類塔羅片語。

  • 依 ## / ### headings 切分；情境解讀 再拆成感情 / 工作 / 自我探索 / 靈性子 chunk
  • 保護塔羅片語；中文保留 2-gram / 3-gram
  • BM25 與 vector 各取 topK，加權合併（bm25=0.45, vector=0.55, graph=0.15），不用 LLM reranker
  • 可選 1-hop graph expansion；用 CLI 與 inspector 離線 eval，改權重後馬上看到差異

沒上 Elasticsearch 或 LLM reranker，是因為想保持可控、可測試、零 DB。
